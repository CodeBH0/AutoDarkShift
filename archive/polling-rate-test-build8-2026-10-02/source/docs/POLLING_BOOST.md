# 轮询 Boost 与频率测试（build 8）

## 操作

1. 在“轮询 Boost 与频率测试”选择关闭、5、10、20、30、60、120、240、500 或 1000 Hz，点击“保存并应用 Boost”。Boost 关闭时使用原“采样间隔”；开启时按所选固定频率替代该间隔。未收到应用确认时，重新开启保活使用保存的档位。阈值、稳定时间、通知冷却继续生效。
2. 开启保活并等待连接，点击“开始逐档频率测试”。测试依次请求 1、5、10、20、30、60、120、240、500、1000 Hz，每档至少观察 10 秒，总计约 100 秒；系统调度延迟可能延长总时长。
3. 测试由扩展内监听执行，不依赖 App 页面刷新。页面只提供控制和操作反馈，测试统计写入日志，不提供实时结果面板。
4. 完成后自动恢复已保存的档位；“停止频率测试并恢复”保留当前档位的部分记录并恢复。保存新配置会结束测试并应用新配置。监听睡眠或停止会保留部分结果，唤醒后使用保存配置。进程异常终止后，下次初始化记录 `polling_test_interrupted`，不把未完成测试当作成功，也不自动继续高频测试。
5. 点击“导出运行日志”，保存 JSONL。共享模式直接包含测试日志；本地模式在运行时通过系统消息或认证本机备用通道分块取回结果并保存到 App；关闭保活后仍可导出已同步部分。未同步的历史结果可重新开启保活后取回。链路修复见 [LOG_TRANSPORT.md](LOG_TRANSPORT.md)。未收到控制回复时，保留“未确认”的含义，通过后续状态或日志确认，不重复启动新的测试来推断旧请求失败。

高频档位增加耗电与发热。建议分别在前台、后台、调节亮度时进行测试，记录设备型号、系统版本、是否低电量模式和调试器状态；对同一设备重复测试后再选择常用档位。

## 测量与判定

每次真实读取 `UIScreen.main.brightness` 前后记录单调时钟，分别统计轮询吞吐和 getter 耗时。系统亮度事件仍参与切换监听，但不加入轮询频率统计。读取相同亮度值是成功读取；`brightnessChanges` 只表示相邻有效读数的变化次数，不能用它推断 API 更新速率。

Apple 的 [brightness 文档](https://developer.apple.com/documentation/uikit/uiscreen/brightness)描述亮度值为 0…1；本工具不假定一个文档承诺的最大读取频率。Apple 的 [Timer 文档](https://developer.apple.com/documentation/foundation/timer)说明定时器并非实时机制，其执行受到 RunLoop 调度影响。因此这里测量的是当前设备、系统和监听负载下，主线程定时轮询加实际 getter 读取可达到的频率，不能区分所有系统内部缓存，也不能作为屏幕刷新率或 API 的硬性限额。

每档的经验性“稳定达到”条件：实际频率达到请求的 90%，轮询间隔 P95 不超过目标间隔的 1.5 倍，没有非法亮度，且每次轮询均取得读取耗时。若 1000 Hz 也达到标准，日志标记 `ceilingSustained=true`，只说明上限尚未在本次扫描范围内发现。测试不会把 1000 Hz 写成 API 最大允许频率。

正常低频采样保留逐条日志。间隔小于 1 秒或测试期间，每个样本在内存更新计数和阈值状态，约每秒写一条样本、一份聚合统计和状态快照；通知结果、生命周期等关键记录仍及时持久化。状态查询不读取亮度，不创造心跳。跨档位重建定时器并丢弃旧回调，不将旧档位的间隔算入新档位。

## 导出字段

所有记录含 `timestamp`、`instanceID`、`event`、`fields`。同一次测试通过 `fields.testID` 关联。

| event | 内容 |
| --- | --- |
| `polling_window` | 普通运行日志中的约一秒轮询聚合窗口；高频档位长期使用时也记录 |
| `polling_test_start` | 测试 ID、全部请求频率、每档时长、原档位、配置版本、经验判定条件 |
| `polling_test_stage` | 每档的实际统计，`completed=false` 表示中止时的部分记录 |
| `polling_test_summary` | 完成或中止原因、完成档数、最高达到标准的请求档位、峰值实际频率、恢复间隔 |
| `polling_test_interrupted` | 下次初始化发现上一个实例的测试未完成 |

| fields | 含义 |
| --- | --- |
| `requestedHz`、`actualHz`、`deliveryRatio` | 请求频率、轮询次数/实际观察秒数、实际/请求频率 |
| `elapsedSeconds`、`polls` | 单调时钟观察时长、真实轮询数 |
| `intervalMeanMs`、`intervalMinMs`、`intervalMaxMs` | 轮询间隔平均、最小、最大值（毫秒）；首个间隔从定时器安装开始算 |
| `intervalP50Ms`、`intervalP95Ms`、`intervalP99Ms` | 间隔分位数（毫秒） |
| `percentileSampleCount` | 参与分位统计的间隔数，最多 20,000；10 秒/1000 Hz 档位可完整保留 |
| `estimatedMissedPolls` | 根据长间隔估计的未到达调度次数，非系统上报的 API 拒绝次数 |
| `apiReadCount`、`apiReadMeanUs`、`apiReadMaxUs` | getter 耗时测量数、平均和最大耗时（微秒） |
| `invalidReadings`、`brightnessChanges` | 非法值数量、相邻有效值变化次数 |
| `sustained` | 是否达到上述经验条件；部分档位不参与汇总的最高频率选择 |
| `highestSustainedRequestedHz`、`peakActualHz` | 已完整测试档位中的最高合格请求档位、最大实际频率；无完整数据时为 `unmeasured` |
| `testedCeilingHz`、`ceilingSustained` | 扫描范围上端 1000 Hz、是否仍达到标准 |
| `completed`、`completedStages`、`reason` | 是否跑完全部档位、已完成档数、结束原因 |

测试开始、分档、汇总和异常中断记录单独保存在 `polling-results-0.jsonl` 与 `polling-results-1.jsonl`，每份最多 32 KiB。普通日志轮转不会挤掉这些结果；测试结果本身也有轮转，建议每次测试后导出。共享导出包含两份文件的完整行，本地通信回复额外附加最多 64 KiB 的测试结果，不经过普通日志尾部裁剪。单个完整测试约十几 KiB，可完整保留。追加前修复异常终止留下的半行；强制终止可能丢失当前档位尚未汇总的内存统计。

## 验证范围

新增 7 项核心回归覆盖旧配置兼容、全部档位、单调计时与亮度事件隔离、高频写入节流且阈值通知仍生效、完整扫描与重试去重、停止/睡眠/重载/进程替换、跨进程与同进程控制、测试日志独立保留和半行修复。模拟读数验证流程与统计，不能替代 iPhone 上真实 getter 耗时、后台调度和温度影响的测量。
